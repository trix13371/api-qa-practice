# Тест-план: личные задачи

## Цель и критерий завершения

Проверить, что пользователь управляет только собственными задачами, данные корректно валидируются и сохраняются. Основание — [контракт версии 2](api-contract.md). Проверки выполняются локально через HTTP, с дополнительными SQL assertions для критичных состояний.

Прогон завершён успешно, если весь автоматизированный набор прошёл, отказанные запросы не изменили данные, а замеченные дефекты исправлены и перепроверены. Это критерий учебной итерации, не разрешение на производственный релиз.

## Риски и трассировка

| Требование | Риск | Сценарий / расположение |
| --- | --- | --- |
| R-OWNER | Чтение, изменение или удаление чужих данных | test_users_cannot_read_or_change_each_others_tasks, test_cannot_choose_task_owner в test_workflows.py |
| R-AUTH | Доступ без действующей сессии | test_invalid_authorization_rejected, test_expired_token_rejected в test_auth.py |
| R-AUTH | Выход не отзывает токен либо завершает все сессии | test_logout_revokes_only_current_session |
| R-AUTH | Перезапись учётной записи при дубликате | test_duplicate_registration_keeps_original_password |
| R-TASK | Ошибочная длина, тип или искажение названия | test_registration_boundaries в test_auth.py; test_valid_titles_round_trip и test_invalid_titles_leave_database_unchanged в test_workflows.py |
| R-UPDATE | Частичная запись при ошибке одного поля | test_rejected_patch_is_atomic: HTTP + SELECT |
| R-DELETE | «Удалённая» задача остаётся доступной | test_task_full_lifecycle |
| R-LIST | Нестабильный порядок или чужая запись в странице | test_filter_and_pagination_apply_to_current_user |
| R-DATA | Потеря записей после перезапуска | test_restart_preserves_users_sessions_and_tasks в test_protocol_and_storage.py |
| R-HTTP | Необрабатываемый ввод или неудобная диагностика | test_invalid_body_rejected, test_oversized_body_rejected, test_request_id_links_response_to_safe_log |

## Техники тест-дизайна

- Граничные значения: username 2/3/32/33, password 7/8/128/129, title 1/100/101 и пустая строка.
- Классы эквивалентности: строка, число, boolean, null, массив, объект; валидный и неверный токен.
- Переходы состояния: невыполнена → выполнена → снова невыполнена → удалена; действующий → истёкший/отозванный токен.
- Комбинации: несколько неверных форматов авторизации на всех защищённых методах; GET/PATCH/DELETE чужого ID; фильтр вместе со страницей.
- Проверка побочных эффектов: повторное чтение и SQL после ошибки, а не только код ответа.

## Окружение и данные

Windows, Python 3.14, зависимости из requirements.txt. Фикстуры создают временную SQLite и HTTP-сервер для каждого теста. Нет зависимости от внешнего сайта или предыдущего прогона. Секреты используются только синтетические.

В большинстве тестов приложение рассматривается как чёрный ящик. SQL используется явно: проверка хранения пароля/токена, владельцев, атомарности, отсутствия лишних записей; подготовка истёкшей сессии. Это смешанный подход, а не заявление о полностью независимом black-box тестировании.

## Ручной исследовательский маршрут

Это план для отдельного ручного прогона, не отметка о выполнении в Postman:

1. Зарегистрировать двух пользователей и получить два токена.
2. Создать задачу первого пользователя; проверить тело ответа и повторное чтение.
3. Вторым токеном проверить список и запросы к ID первого пользователя.
4. Отправить PATCH с верным title и неверным completed; проверить прежние данные API и SQL.
5. Проверить комбинированный фильтр и страницу, затем удаление и повторный GET.
6. Перезапустить сервис, войти ещё раз, сопоставить API со SQL-запросами из sql-checks.sql.
7. Записать X-Request-ID ошибки и найти соответствующую запись в логе. Для дефекта сохранить запрос, фактический и ожидаемый результат без действующего токена.

## Непокрытые риски

Нагрузки, конкурентные обновления и блокировки БД; гонка при регистрации; миграции схемы; резервное копирование; все комбинации некорректных тел на каждом маршруте; все Unicode-пробелы; точная временная граница истечения; ограничения попыток входа; HTTP через обратный прокси. Health — простая проверка запроса к БД, не комплексный мониторинг.

Нет UI, поэтому кроссбраузерное тестирование к этому проекту не относится. Результаты этой итерации: [отчёт](test-results.md).
