# Контракт Task API, версия 2

Сервис личных задач. Пользователь создаёт и видит только собственные задачи. Это требования учебного проекта, а не описание стороннего API. Изменение требований должно сопровождаться обновлением проверок.

## Ресурсы и статусы

| Метод и путь | Успех | Основные ошибки |
| --- | --- | --- |
| GET /health | 200, {"status":"ok"} | Проверяет возможность запроса к БД |
| POST /users | 201, {"id":1,"username":"qa_user"} | 400: неверные поля; 409: имя занято |
| POST /auth/login | 200: access_token, token_type, expires_in | 400: структура; 401: неверные учётные данные |
| POST /auth/logout | 204, пустое тело | 401: токен недействителен |
| POST /tasks | 201, созданная задача | 400: данные; 401: авторизация |
| GET /tasks | 200, массив задач | 400: параметры; 401: авторизация |
| GET /tasks/{id} | 200, задача | 401 или 404 |
| PATCH /tasks/{id} | 200, обновлённая задача | 400, 401 или 404 |
| DELETE /tasks/{id} | 204, пустое тело | 401 или 404 |

## R-AUTH: регистрация и сессии

Регистрация и вход принимают ровно username и password. Неизвестные и отсутствующие поля — 400. Корень тела — JSON-объект, тип Content-Type — application/json или JSON-совместимый тип.

- username: строка из ASCII-букв, цифр и подчёркиваний; длина 3–32 включительно. Регистр значим.
- password при регистрации: строка 8–128 символов, не только пробельные символы. Сохраняется хеш, не исходный пароль.
- Занятое имя не меняет существующий пароль.
- Неизвестное имя и неверный пароль при входе дают одинаковый ответ 401: {"error":"Invalid credentials"}.
- Успешный вход: {"access_token":"…","token_type":"Bearer","expires_in":3600}.
- Токен непрозрачный, не JWT. Для доступа: Authorization: Bearer <token>. В БД хранится SHA-256 токена.
- Нет токена, неверный формат, истёкший или отозванный токен — 401 и WWW-Authenticate: Bearer.
- Каждый вход создаёт отдельную сессию. Выход отзывает только текущую сессию. Повторный выход с ней даёт 401.
- В учебном тесте срок истечения меняется через SQL при подготовке; запрос всё равно отправляется через HTTP.

## R-OWNER: принадлежность

Владелец определяется сессией, а не телом запроса. Задать owner_id нельзя. Список не содержит чужих задач. Чужой и несуществующий числовой ID возвращают одинаковые 404: {"error":"Task not found"}. Перед проверкой существования задачи проверяется авторизация.

## R-TASK: создание и чтение

POST /tasks принимает только обязательное поле title:

```json
{"title":"Review requirements"}
```

title — строка длиной 1–100 Unicode-кодовых точек включительно. Пустая строка, строка только из пробельных символов и U+0000 запрещены. Остальные символы, включая @@@, кавычки, кириллицу и эмодзи, разрешены. Пробелы в непустом названии сохраняются.

ID — положительное целое, назначается сервером. Новая задача completed=false. Ответ не содержит владельца, пароля или токена:

```json
{"id":1,"title":"Review requirements","completed":false}
```

## R-UPDATE: атомарное изменение

PATCH принимает непустой объект с title и/или completed. Правило title совпадает с созданием; completed — только JSON boolean, не 0, 1, строка или null. Неуказанные поля сохраняют прежнее значение. Неизвестные поля — 400.

Сначала валидируется весь запрос. Если хотя бы одно поле неверно, ни одно изменение не записывается. GET после успешного PATCH возвращает новые значения.

## R-DELETE: удаление

После успешного DELETE задача отсутствует в списке и недоступна по ID. Повторное удаление возвращает 404, не восстанавливает данные. Удаление чужого ID не меняет задачу владельца.

## R-LIST: фильтрация и страницы

Допустимы только completed, limit, offset; каждый параметр не более одного раза.

- completed: буквально true или false; без него возвращаются оба состояния.
- limit: ASCII-цифры, 1–100 включительно, по умолчанию 100.
- offset: ASCII-цифры, 0–2147483647 включительно, по умолчанию 0.
- Знаки, дроби, пустые значения и неизвестные параметры отклоняются.
- Порядок — ID по возрастанию. Сначала ограничение владельцем и фильтрация, затем offset/limit.
- Пустой результат и страница за концом списка: 200 и [].

## R-DATA: сохранность

Пользователи, сессии и задачи сохраняются в файловой SQLite. Перезапуск приложения с тем же файлом не очищает данные и не обнуляет ID. Отклонённый запрос не создаёт и не меняет задачи. Разные тесты используют разные файлы БД.

## R-HTTP: ошибки и диагностика

Для ожидаемых ошибок тело — {"error":"…"}. Примеры: JSON object required, Task not found, Authentication required. Тело запроса больше 64 KiB — 413; неизвестный маршрут — 404; неподдерживаемый метод — 405 с заголовком Allow, перечисляющим допустимые методы.

Ответ содержит X-Request-ID (UUID) и Cache-Control: no-store. При штатной обработке в лог записываются request_id, method, path, status и duration_ms. Тело и Authorization в этот лог не включаются. timeout=3 в тестах — ограничение ожидания, не SLA производительности.

Неожиданные внутренние исключения не являются частью описанного формата ожидаемых ошибок.
