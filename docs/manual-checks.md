# Ручные проверки Task API в Postman

Отчёт о ручном тестировании подготовлен 26 октября 2026 года. Он отражает выполненные проверки в Postman; это не повторный прогон всех вариантов автоматизированного набора. Скриншоты с действующими токенами не публикуются; пароли и значения токенов в отчёт не включены.

Два пользователя обозначены A и B. В историческом прогоне задача 1 принадлежала A, затем была удалена владельцем; новая задача 2 также принадлежала A, задача 3 - B. Эти номера описывают прошлый прогон, а не универсальные входные данные для повторного тестирования.

## Подтверждённые результаты

| Проверка | Ожидание и фактический результат | Итог |
| --- | --- | --- |
| Регистрация пользователя A | 201; ответ содержит id и username, без пароля | PASS |
| Вход пользователя A | 200; получен токен для дальнейших запросов | PASS |
| Создание и чтение своей задачи | POST 201, GET 200; название и id совпали, completed=false | PASS |
| Выполнение своей задачи | PATCH 200; последующий GET 200 подтвердил completed=true и прежнее название | PASS |

| Запрос без авторизации | 401, Authentication required; данные задачи не выданы | PASS |
| Запрос с недействительным токеном | 401; использовано значение invalid-token | PASS |
| Регистрация и вход B | Регистрация 201, вход 200; получена отдельная сессия | PASS |
| Чтение чужой задачи | GET от B дал 404; контрольный GET от A дал 200 | PASS |
| Изменение чужой задачи | PATCH с корректным JSON от B дал 404; GET от A подтвердил прежние данные | PASS |

| Выход отзывает текущий токен B | POST /auth/logout дал 204; GET списка с прежним токеном дал 401 | PASS |

## Что нельзя считать подтверждённым этим отчётом

- Сохранность задачи после повторного входа B не подтверждена историческим ручным прогоном; в новой коллекции предусмотрен отдельный сценарий.
- Фильтрация, пагинация, истечение сессии и сохранность после перезапуска покрыты автотестами; полный ручной прогон этих вариантов здесь не заявляется.
- В экспортированной учебной коллекции было 18 целевых запросов, но это не 18 готовых автоматических Postman-тестов: у основных запросов не было assertion-скриптов, использовались фиксированные id и ручной порядок.

Для повторного прогона создавать отдельные учебные данные и брать id из ответов. После ошибочного или запрещённого изменения проверять состояние через GET владельца. Для проверки запрета изменений использовать PATCH с корректным телом и токеном другого пользователя. Для проверки запрета удаления использовать DELETE с токеном другого пользователя; удаление владельцем проверяется отдельно.
