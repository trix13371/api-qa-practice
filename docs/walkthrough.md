# Как разобрать проект и уверенно рассказать о нём

Начни не с Flask, а с контракта и одного сценария. Нужно уметь объяснить, что проверяет тест и почему результат именно такой.

## Порядок изучения

1. docs/api-contract.md: права владельца, коды ответов, ограничения полей.
2. tests/test_tasks.py: создание и повторное чтение; отдельная негативная проверка сохранности.
3. tests/test_workflows.py: жизненный цикл и два пользователя.
4. tests/conftest.py: временная БД, HTTP-сервер, клиент и авторизация.
5. tests/test_auth.py: истечение и отзыв сессии.
6. tests/test_protocol_and_storage.py: перезапуск и связь ответа с логом.
7. application.py, storage.py, schema.sql: как требования реализованы.
8. docs/bug-report-001.md: как тест обнаружил дефект и что изменилось после исправления.

## Что важно в тестах

Arrange → Act → Assert: сначала данные и условия, затем запрос, затем сравнение с ожиданием из требований. Нельзя считать ответ правильным только потому, что он 200: проверяются поля, повторное чтение и сохранённое состояние.

Параметризация запускает один сценарий с разными данными. Поэтому число результатов pytest больше числа тестовых функций. В регистрации проверяются значения ниже границы, на границе и выше неё. Для completed выделены разные типы: число 1 не равно JSON boolean true по контракту.

Тест двух пользователей проверяет не только 404 на чужой ID, но и сохранность данных владельца. Тест атомарного PATCH отправляет валидный title вместе с неверным completed: title тоже не должен измениться.

SQL assertions — дополнительный источник проверки, не замена запросам к API. Они помогают увидеть неправильного владельца или запись после отклонённого запроса.

## Фикстуры

app создаёт приложение с новой БД в tmp_path. api_url поднимает настоящий сервер на порту 0, который выбирает ОС. anonymous_http — requests.Session без токена, http — отдельный зарегистрированный пользователь с Bearer-токеном. login_as позволяет создать второго пользователя.

Ресурсы освобождаются после yield, даже когда assert падает. Нет жёстко заданного порта, общих постоянных аккаунтов или зависимости от предыдущего теста. trust_env=False отключает окружение прокси для этих локальных запросов.

В тесте перезапуска намеренно используется один и тот же файл: первый сервер закрывается, затем создаются новое приложение и новый сервер. В тесте истечения токена время в записи меняется на уже прошедшее — ждать час не требуется.

## Небольшая самостоятельная доработка

Добавь сценарий: два входа одного пользователя → создание задачи с первым токеном → чтение вторым токеном → выход первого → вторым задача по-прежнему доступна. Сначала напиши ожидаемые результаты, потом тест, запусти и объясни его.

Готовый код полезен как учебная основа. Перед собеседованием стоит пройти этот разбор и самостоятельно изменить хотя бы один тест; не приписывай себе опыт, которого ещё нет.
